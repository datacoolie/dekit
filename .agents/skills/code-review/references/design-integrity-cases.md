# Design integrity: paired cases

Use only to calibrate ambiguous design or wiki findings. These authored examples illustrate [design readiness](../../../instructions/artifacts.md#design-contracts-and-work-item-readiness), [implementation constraints](../../../instructions/engineering-constraints.md), [conformance checks](../../../instructions/verification.md#design-conformance-and-refactoring), and [wiki discrepancy handling](../../../instructions/wiki.md#discrepancy-handling). They are not live-agent evaluations or extra policy.

| Case | Evidence to inspect | Action / counterexample |
|---|---|---|
| C1: required attribute defaulted | Base constructor guarantees `config`; subclass uses `getattr(self, "config", None)`. Trace supported constructors, callers, and failure behavior. | Report a contract violation if the default hides failed initialization. If `config` is optional on a supported path, the default may be correct; do not infer a guarantee from one constructor. |
| C2: getter or lazy access | `get_config()` validates access or acquires a resource lazily; an optional adapter has a documented fallback. | Preserve the mechanism when it serves the contract. A forwarding wrapper is only a simplification candidate when callers, compatibility, and extension behavior show no remaining role. |
| C3: duplicate state/rule | Two independently writable owners define the same business rule/state and can disagree. Trace writes, reads, and lifecycle. | Identify the authoritative owner and concrete divergence risk. Explicitly derived/cache state with a supported invalidation lifecycle is a counterexample, not automatic duplication debt. |
| C4: component role | A parser reaches into another component's private state or launches unrelated jobs; inspect accepted roles and call direction. | Report the specific boundary violation or maintenance cost. An explicitly designated coordinator legitimately composes and runs components; orchestration itself is not a smell. |
| C5: stale descriptive wiki | An authorized deployment change is verified in configuration/tests, but the architecture diagram or runbook still describes the old topology. | In assigned repair, update the affected knowledge and references. In health-only review, report stale claims and disposition without writing or running unsafe production commands. |
| C6: implementation drift | Code permits a behavior forbidden by the effective accepted spec/decision. Confirm applicability, replacement decisions, and actual behavior. | Report implementation drift; do not rewrite the requirement to match code. Unknown authority or conflicting evidence requires a discrepancy and next check, not a guessed fix. |
| C7: conflicting/history pages | Two current pages disagree, or a former decision has an accepted replacement. Inspect ownership, evidence, and lifecycle. | Reconcile current claims through their canonical owner within authorized scope; retain old rationale and link supersession. An old date, changed hash, or live link cannot decide which claim is correct. |
| C8: cleanup versus redesign | A local extraction supports the authorized task; a proposed change also moves shared state or changes inheritance/contracts elsewhere. Inspect scope and existing authorization. | Verify bounded cleanup; propose consequential redesign when no approach is established. Proceed with an already authorized design without requesting the same permission again. |
| C9: SQL/notebook boundary | A transform and an unrelated I/O path each define the same metric or keep incremental state. Inspect grain, null/schema semantics, side effects, and accepted ownership. | Consolidate the authoritative rule or isolate I/O when justified, preserving data contracts and idempotency. A clear functional pipeline need not become classes/interfaces. |

For a walkthrough, record the cited evidence, disposition, smallest justified action (including no change), and remaining uncertainty. For structural refactoring, compare the intended ownership/caller/dependency outcome as well as behavior; passing tests alone is insufficient evidence for the structural claim.
