# FastAPI relational persistence

- Pick SQLAlchemy when it fits the project's relational persistence needs. Select the sync or async driver with the execution model and target platform in mind. For SQL Server, verify the system ODBC driver as well as the Python dependency. SQLAlchemy's `mssql+aioodbc` dialect uses a thread-backed interface to pyodbc.
- Create engines and session factories in the process that owns them and dispose engines at shutdown. Budget pool and overflow capacity across API workers, replicas, and job processes.
- Scope sessions to the operation. A `Session` is for one thread at a time and an `AsyncSession` is for one task at a time. Give queued work its own session. Apply [transaction ownership](../../python-development/references/application-design.md#transactions). Avoid commits in both dependency teardown and the use case, and roll back failures before reusing a session. Resolve commit failures before reporting HTTP success.
- Keep transactions short around database work. Use projections or eager loading to materialize required fields before serialization. `expire_on_commit=False` leaves loaded values available but leaves unloaded relationships unloaded. Inspect for N+1 queries and measure query plans and indexes when material.
- Bind SQL values and enforce invariants with database constraints where appropriate. Handle concurrent constraint failures explicitly. Exercise the actual target database when claiming support for its types, constraints, locking, or migration behavior.
- For an app-owned schema, use the project's migration workflow. Review Alembic's generated operations, especially renames and data transformations. Keep historical revisions independent of evolving models and test upgrades from a representative prior schema. Run production migrations as a controlled deployment operation with an explicit recovery path. Coordinate compatibility across versions during a rolling change.
