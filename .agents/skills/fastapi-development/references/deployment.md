# FastAPI deployment

- If deploying a container, install from the project's reproducible artifact or lock workflow. Keep credentials and local env files out of the image and build context. Use a non-root user when feasible and provision needed writable paths explicitly.
- Launch the documented ASGI target without development reload. Use an exec-form command or a supervisor that forwards termination signals. Size workers and replicas for CPU, memory, and connection budgets. When an orchestrator manages replication, one serving process per container is a reasonable starting point.
- When adding operational probes, default to `/health/live` and `/health/ready`. Use liveness to detect a process that needs restarting. Keep it independent of transient downstream outages. Use readiness to indicate whether the instance can accept work. Bound checks for required startup and dependencies, and return a status the platform treats as unavailable. Use a startup probe when initialization would otherwise trigger premature restarts.
- Verify external URLs, redirects, and OpenAPI behind the actual proxy. Treat `root_path` as the mount prefix in the ASGI scope. Keep app route prefixes in the router and trust forwarded headers only from known proxies. Check body limits, TLS, and timeouts at their owning boundary. Choose docs paths and visibility to suit the deployment and client contract.
- Correlate requests and jobs using safe identifiers. Collect useful latency, error, readiness, queue, and resource signals. Verify image startup, traffic admission, and shutdown with the relevant production-like dependencies. Allow bounded draining on shutdown and coordinate rolling compatibility with the [migration workflow](database.md) when the rollout changes the database.
